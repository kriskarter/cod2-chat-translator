# CoD2 Chat Translator — Release Process

Этот документ — источник истины для будущих чатов при выпуске релизов.

## Проверенный patch / hotfix

Если RC уже реально проверен пользователем в Windows / CoD2 и пользователь подтвердил, что всё работает, предпочтительный процесс — автоматическая gated-цепочка без ручного дробления каждого шага.

Порядок:

1. Работать из проверенной ветки `hotfix/**` или `feature/**`.
2. Подготовить новую версию:
   - `APP_VERSION`;
   - fallback-версию установщика;
   - `release_notes.json`;
   - README RU / UK / EN;
   - примеры конфигурации;
   - version-sensitive тесты.
3. Локально выполнить:
   - `python -m py_compile`;
   - полный `unittest`;
   - `git diff --check`.
4. Закоммитить и отправить release-preparation commit в проверенную ветку.
5. Ждать `build-release-candidate.yml` именно для этого commit SHA.
6. Если RC красный — STOP. Ничего не сливать.
7. Если RC зелёный — выполнить только fast-forward:
   `git merge --ff-only`.
8. Push `main`.
9. Ждать `build-windows.yml` именно для release commit SHA в `main`.
10. Если stable Windows build красный — STOP. Тег не создавать.
11. Если stable build зелёный — создать и push тег `vX.Y.Z`.
12. Дождаться публикации GitHub Release.
13. Только после появления Release считать выпуск завершённым.

## Главное правило

Для уже проверенных patch/hotfix-релизов использовать автоматическую цепочку:

`local tests → RC → main → stable Windows build → tag → GitHub Release`

Каждый следующий этап выполняется только после успешного предыдущего.

CI нужно отслеживать по точному commit SHA, а не просто по имени ветки.

## Для больших релизов

Для нового minor/major релиза (`v1.18.0`, `v2.0.0`) или крупной новой функции обязательно оставлять ручную остановку после RC.

Сначала пользователь:
- скачивает RC;
- устанавливает;
- проверяет реальные сценарии в игре;
- явно подтверждает, что всё работает.

Только после этого:
`main → stable build → tag → release`.

## Запрещено

- Не force-push `main`.
- Не исправлять расхождение веток через force-push без разбора причины.
- Не двигать существующий release tag.
- Не удалять старые release tags.
- Не переиспользовать уже существующий номер версии.
- Не создавать тег до зелёной stable Windows-сборки.
- Не считать локальные тесты заменой Windows RC.
- Не выпускать экспериментальный overlay/code без ручной проверки в игре.

## GitHub Actions

RC workflow запускается для:

- `feature/**`
- `hotfix/**`

Stable workflow запускается при push в:

- `main`

Публикация Release запускается тегом:

- `v*`

## История решения

Полная автоматическая gated release-цепочка впервые применена при выпуске `v1.17.2`.

К этому моменту пользователь уже вручную проверил RC в реальной игре.

В `v1.17.2` также был заменён старый Windows Tk/chroma-key incoming overlay на нативный per-pixel alpha overlay после диагностики редкой чёрной вспышки.

Для будущих уже проверенных patch/hotfix-релизов этот автоматический процесс считается предпочтительным, потому что уменьшает количество ручных действий и вероятность ошибки.
